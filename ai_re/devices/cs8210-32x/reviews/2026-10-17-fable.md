## prioritized findings

**1. high (actual gap in the candidate dts): vendor no-map reservations are dropped.**
both vendor dtbs carry a `reserved-memory` node with three no-map regions: ecc poison pages at 0x1e0000 and 0x1e1100, and a 256 mib `apcea_reserved` region at 0xb0000000..0xc0000000 (`analysis/celestica_cs8210-r0.dts:3199-3218`, same in `analysis/kernel-review/celestica_cs8210-r0_12v_21.dts:3132-3151`). the candidate `bringup/cs8210-serial.dts` keeps only the upstream 1 mib secmon reservation. the stored boot log confirms the layout matters: cma was placed at 0xaf000000 (`vendor-dmesg.txt:6`), i.e. directly below the reserved window, bank 0 ends near 0xb0000000 (dma zone 720893 pages, `vendor-dmesg.txt:10`) and a second bank runs to 0x240000000 (`vendor-dmesg.txt:46`). the firmware clearly expands the memory node beyond the packaged 1 gib stub (7.75 gib seen, `vendor-dmesg.txt:33`), so the mainline kernel will see the whole map and can allocate page tables, initramfs pages or the printk buffer inside the window that firmware or a secure agent considers its own. consequence ranges from silent corruption to a hang that looks like a serial problem. correction: copy the three vendor reserved-memory children into the candidate dts verbatim, and mention in `bringup/README.md` that the 0x04000000/0x10000000/0x30000000 placements are all inside bank 0 below 0xaf000000.

**2. medium-high (hypothesis, first-boot blocker if true): architected timer frequency source.**
the packaged vendor dtb sets `arch-timer` `clock-frequency = <0x2faf080>` (50 mhz) at `analysis/celestica_cs8210-r0.dts:198`, but the stored log reports the counter at 75 mhz (`vendor-dmesg.txt:56,58`). linux 4.9 prefers a dt `clock-frequency` over cntfrq_el0, so the runtime dt either had 75 mhz patched in by u-boot or had the property removed. none of the project documents notice this. upstream `alpine-v3.dtsi:301-307` has no `clock-frequency`, so 7.2.11 relies entirely on cntfrq_el0 (`arm_arch_timer.c:864-876, 1187-1188`). if the el3 monitor leaves cntfrq unprogrammed, the kernel prints "frequency not available" and stalls before the first scheduler tick, which would be indistinguishable from a console failure on a first boot. deciding observation: under stock linux, read `/proc/device-tree/soc/arch-timer/clock-frequency` and compare with the packaged 50 mhz. if the live value is 75 mhz, the firmware is editing the dt and cntfrq may or may not be set. recommended correction now: build a second dtb variant with `timer { clock-frequency = <75000000>; }` so the live session can retry without a rebuild, and add the `/proc/device-tree` check to the preflight list.

**3. medium (procedure gap): u-boot will replace the dts bootargs.**
`bringup/cs8210-serial.dts:15` embeds `earlycon=... ignore_loglevel keep_bootcon panic=0 rdinit=/init`. u-boot's chosen fixup overwrites `/chosen/bootargs` with the env `bootargs` whenever that variable is non-empty, and the stock env sets `root=/dev/sda3 init=/sbin/init rw rootwait` (`vendor-dmesg.txt:23`). the kernel would still run the embedded initramfs `/init`, so boot would not fail, but earlycon and keep_bootcon, the only diagnostics that matter on a failed boot, would be lost. `bringup/README.md:99-115` says commands will be built live but never mentions this. correction: in the first-session procedure, explicitly `setenv bootargs` (not saved) with the candidate string before `bootm`, and record `fdt_high`, `initrd_high`, `bootm_size` and `bootm_low` during `printenv` since they govern where u-boot relocates the dtb.

**4. medium (overstatement in offline-research.md): the pci coherency reference does not match the cs8210 dt's gating.**
`offline-research.md:62-69` presents `pci-internal-alpine.c:128-154` as the register sequence the stock kernel ran. the sequence matches the log string, but the reference only registers the notifier when the host node has `dma-coherent` (`pci-internal-alpine.c:357-361`), and the vendor `pcie-internal` node has no such property (`analysis/celestica_cs8210-r0.dts:1275-1289`); the vendor instead has `ccu { io_coherency = <1> }` at line 213-217. so the stock driver is gated differently from the reference. also, because the notifier hangs on the global pci bus type, it fired for the external root ports too (`vendor-dmesg.txt:281,312,343`), which the doc frames as internal-only. correction: state that the gating condition is unknown and that external root ports received the same writes; both matter for the innovium milestone.

**5. medium (useful fact missing from kernel-review.md): stock ran without msi.**
every host bridge logged "annapurna labs msi chip not found!" (`vendor-dmesg.txt:191,261,293,324`) and al_eth fell back with "of_irq_parse_pci() failed" (`vendor-dmesg.txt:590`). the stock kernel therefore served sata, both nics and the innovium link on legacy interrupts. `kernel-review.md:87` treats the msix `interrupt-controller` fix as a prerequisite; for parity with stock it is not, and the first pci milestone can be planned on intx only. this lowers risk, so it is worth recording.

**6. low (harness weakness): the fan_max_speed "input 0 sets bit" claim is not demonstrated by the trace.**
`trace_cpld.py:49` seeds every register with 0xa5, which already has bits 7 and 5 set. the input-0 traces therefore write back 0xa5 unchanged (`cpld-setter-traces.json:16-21, 46-51`), so `board-control.md:45-46` rests on reading the disassembly, not on the emulation. correction: run each case with a second seed (0x00 or 0x5a) and keep both in the json. the hand-resolved switch-table patch at `trace_cpld.py:59-62` does match `sys-cpld-disassembly.txt:1259-1266`, and the ipd dispatch derivation at `extract_ipd_abi.py:53` matches `ipd-ioctl-disassembly.txt:48-55`, so those parts hold.

**7. low (rerun hazards, acquisition scripts).**
`scripts/verify.py:16` refuses to run while `analysis/ssd.img.partial` exists, and `scripts/acquire.py:38` opens `evidence/read-errors.txt` exclusively, so any aborted attempt needs manual cleanup before a retry. both are deliberate and safe; document them. the integrity claim itself is correctly bounded: the sha-256 is computed on the single dd stream and the archive is verified against that same stream (`acquire.py:35-53`, `verify.py:21-39`), so it proves archive-equals-read, not archive-equals-media. dd without `conv=noerror,sync` aborts on error (`acquire.py:39`), so the "no zero substitution" statement is right, and `read-errors.txt` is empty. `ssd-analysis.md:149` still names the old `inspect.py`.

**8. low (documentation drift).** `kernel-review.md:143` cites a dmc12 dtb staging address of 0x04078000 that i could not locate anywhere in the local dmc12 checkout; the msix, clock, and pcie `config/controller/dbi` claims do appear in `dmc12-nixos/kernel/dts/amazon/alpine-v2-dmc12.dts:52-54,90,125`. the 21-inch variant also describes a marvell `mv88e6141` dsa switch (`celestica_cs8210-r0_12v_21.dts:2939`), which means management ethernet differs per variant; the ethernet plan should note it.

## what checks out

the load-address correction is sound: `arm64-header.json` shows text_offset 0 and image_size 6,094,848, `mkimage.txt` shows load/entry 0x04000000, and `booting.rst:138-142` requires text_offset above a 2 mib base; the stock 0x04080000 with text_offset 0x80000 is the same base. `CONFIG_RELOCATABLE` is off (`serial-build/.config:473`), so that alignment is mandatory, and the build enforces it. the uart description matches the stock log exactly: ns16550a, reg-shift 2, io width 4, base_baud 31250000 from a 500 mhz clock, detected as 16550a (`vendor-dmesg.txt:358`), with the generic 8250 path and not 8250_dw, which is what `serial.config` selects. psci 0.2, gicv3 register map, cortex-a72 r0p3, and el2 entry all agree between the stored log and the upstream dtsi. the revision-4-to-2 ethernet mapping is literally `al_hal_eth_main.c:1089-1094` with `al_hal_eth.h:108-113`. the i2c mux paths, bus numbers (8-0060, 11-0064, 23-0063, 31-0066, 40-0066, asc on bus 20), top/bottom fan labels and the board-variant discriminator all reconcile with `install.sh:15-90` and `install-platform:15-67` under a depth-first numbering model. the onie unpacker validates the payload sha-1 and fit crcs as data and creates no links or device nodes.

the qemu test is honestly scoped in `bringup/README.md:3-6`: it boots the raw image with qemu's own dt and pl011, so it exercises the kernel, embedded initramfs, loader, 4 cpus and el2 entry, and nothing about the board dtb, 8250, the uimage wrapper, or 16 cpus. it is not false confidence as written, but readers of `PROGRESS.md:37-39` should keep that sentence in mind.

## verdict on first live boot

not ready for a blind attempt, but close. there are no critical bugs in the scripts or packaging. the two things that could turn a first boot into an unexplained silent hang are finding 1 (missing no-map regions, a certain omission) and finding 2 (timer frequency, a hypothesis with a cheap live test). with those addressed and the bootargs procedure written down, the serial candidate is a plausible first trial that does not depend on pci, dma, or board drivers.
