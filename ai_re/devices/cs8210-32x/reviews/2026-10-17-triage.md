## accepted findings, in first-boot priority order

### 1. High: explicit-baud earlycon programs the wrong divisor

Confirmed in `bringup/cs8210-serial.dts:15` and upstream 7.2.11
`drivers/tty/serial/earlycon.c:125-149`,
`drivers/tty/serial/8250/8250_early.c:130-170`.

The explicit-address `earlycon=uart8250,mmio32,0xfd883000,115200n8` does not obtain
the UART clock from DT. It defaults to 1,843,200 Hz, computes divisor 1 and writes
that divisor. At the stock log's 500-MHz UART clock this gives 31.25 Mbaud,
losing readable early diagnostics. The later regular OF serial driver may repair
the divisor; this is not evidence of a kernel crash. QEMU uses PL011 and did not
exercise this path.

Recommended correction: use `earlycon=uart8250,mmio32,0xfd883000` to retain the
working firmware divisor. Keep the normal `console=ttyS0,115200n8` setting.
The focused Fable review independently confirmed this source trace. Its comment
about `keep_bootcon` is qualified in that report: retaining the early console
does not prevent the regular driver from restoring the shared hardware divisor.

### 2. High: candidate omits vendor no-map reservations

Confirmed omission in the board candidate. Both recovered DTs reserve:

| Region | Start | Length |
| --- | --- | --- |
| ECC poison channel 0 | `0x001e0000` | `0x1000` |
| ECC poison channel 1 | `0x001e1100` | `0x1000` |
| APCEA | `0xb0000000` | `0x10000000` |

See `analysis/celestica_cs8210-r0.dts:3199-3218`. Upstream's retained secmon
reservation covers only the first MiB, so it does not cover the ECC areas.
Preserve the vendor reservations alongside secmon, rebuild, and inspect the
compiled DT. The channel-1 address is unusually unaligned; preserve the evidence
and check the resulting page reservation rather than silently normalizing it.

The broad review overstates the inevitable consequence of the high reservation:
we do not know whether firmware will expand this candidate's 1-GiB memory entry,
or whether its resulting banks already exclude APCEA. The historical log proves
that the old kernel saw much more RAM than the packaged stub describes, not how
this new DT will be modified. Missing reservations create a corruption risk if
those regions become allocatable; no corruption has been observed. Capture the
live DT, firmware memory map and `/proc/iomem` before choosing load addresses.

### 3. Medium: timer source discrepancy needs a live check

Confirmed evidence mismatch: the packaged DT declares 50 MHz
(`analysis/celestica_cs8210-r0.dts:198`), while the historical log reports 75 MHz
(`analysis/kernel-review/vendor-dmesg.txt:56-58`). The mainline candidate has no
explicit timer rate and therefore uses CNTFRQ unless firmware adds an override.
See 7.2.11 `drivers/clocksource/arm_arch_timer.c:864-876,1187-1188`.

This does not establish that CNTFRQ is wrong or that the candidate will hang.
Firmware fixups, a different runtime DT, or vendor-kernel behavior could explain
the discrepancy. Read the runtime timer node and CNTFRQ where accessible, then
check timekeeping on hardware. A separately named 75-MHz experimental DT is a
reasonable fallback to prepare; it must not become an unexplained default.
Blindly copying the packaged 50-MHz value is not supported by the boot log.

### 4. Medium: make command-line handoff explicit

The first-session procedure should capture `bootargs`, `fdt_high`, `initrd_high`,
`bootm_size` and `bootm_low`, then explicitly establish the intended temporary
command line and verify the DT passed to Linux. Ordinary U-Boot chosen-node
fixups can replace DTS bootargs from the environment. The historical stock
command line lacks the candidate's early diagnostics. Exact installed U-Boot
behavior and saved environment remain unverified.

Use the corrected earlycon string, and do not save the experimental environment.
RAM addresses remain proposals pending live memory/relocation checks, so this
review does not promote a generic `bootm` example into a validated boot procedure.

## accepted qualifications and lower-priority follow-ups

- **PCI coherency gating:** the public reference registers its global PCI-bus
  notifier only with host `dma-coherent`
  (`analysis/research/mikrotik-added/drivers/pci/controller/pci-internal-alpine.c:357-361`).
  The packaged board's internal host lacks that flag and instead describes
  `ccu.io_coherency=1`. The old log also prints the matching callback message for
  external root ports (`vendor-dmesg.txt:281,312,343`). The common initialization
  lineage is useful, but exact gating and every register write in the installed
  kernel are unproven. Existing notes already qualify instruction equivalence;
  add the gating and external-port scope before implementing a mainline fixup.
- **Fan emulation coverage:** the only seed is `0xa5`, whose bits 7 and 5 are
  already set (`scripts/trace_cpld.py:49`). Thus input-zero fan cases do not
  independently demonstrate setting those bits. Disassembly supports the
  interpretation; add a contrasting seed such as `0x5a` and validate both.
- **Acquisition reruns:** exclusive output creation is a deliberate safeguard.
  Document inspection/cleanup of interrupted partial outputs, rather than
  removing the safeguard. The existing verification proves the archive equals
  the bytes read during acquisition; it is not a second independent media read.
- **Stale name:** `ssd-analysis.md:149` still says `inspect.py` in prose; the
  executable example correctly uses `scripts/inspect_ssd.py`. Correction pending.

## findings rejected or narrowed after source checks

1. **“DMC12 staging address unverifiable” — rejected.**
   `analysis/kernel-review/dmc12-nixos/uboot-menu/builder.sh:154,158` explicitly
   loads the DT at `0x04078000` and passes that address to `bootm`. Keep the
   existing warning about copying this layout with a larger CS8210 DTB.
2. **“21-inch DT proves different management switch wiring” — rejected.**
   Both DTs contain the same disabled `eth-switch` node with model `mv88e6141`:
   normal DT lines 3004-3009, alternate DT lines 2937-2942. This node establishes
   neither a variant difference nor an active DSA implementation.
3. **“All stock SATA/NIC/Innovium traffic used legacy interrupts” — unproven.**
   The host logs do say MSI chip not found, but `of_irq_parse_pci()` failure is
   not evidence of a successful legacy-IRQ fallback. The same log describes
   vendor AHCI custom IRQ handling and separate port IRQs (lines 374-382), and
   initializes Alpine IOFIC (line 55). Enumeration of Innovium does not prove
   its traffic or interrupt path worked. Capture `/proc/interrupts`, PCI MSI
   state and driver behavior under stock Linux before drawing that conclusion.
   Upstream's `board_ahci_al` disables MSI, so SATA INTx remains a concrete
   initial path; this was already documented. The existing MSI table is not a
   serial-boot prerequisite, and MSI/PCI are disabled in the serial candidate.
