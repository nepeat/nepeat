## 2. Mechanism (V = verified, I = inference)
- V: libifcs.so (sha256 388031e7..., the SONiC and vendor-stack copy) im_malloc @0x46625c = malloc(n), then, when
  the result is not NULL, memset(p, 0, n). The learn thread calls im_malloc(n * 8) with n from its ring producer
  index (2026-11-10 review: one read of BAR0 +0x4860; all-ones gives n = 0xFFFFF801 for an idle ring, a request
  of 0x7FFFFC008 B, mapped as 0x7FFFFD000 = 34359726080 B = 33554420 kB).
- V: syncd VmSize normally 1692496 kB (this boot's restarted syncd, same build). 35246804 - 1692496 = 33554308 kB:
  one extra mapping of 32 GiB within 0.0003 % of the learn thread's request.
- V: vm.overcommit_memory = 1 on this system, set by nixpkgs' services.redis.vmOverCommit (default true; SONiC's
  redis has save = [] and appendOnly = false, so it does not need it). On 2026-11-10 (vendor stack, no redis) it was
  0: the same request failed ("__vm_enough_memory: ... comm: ifcs-learn, bytes: 34359726080"), malloc returned NULL,
  im_malloc skipped the memset, the thread spun at 100 % with a log flood: the line the ifcs watchdogs key on.
  With 1, malloc succeeds and the memset faults in pages at GB/s: no kernel line, a global OOM in seconds.
- I (high): the bad index came from a BAR read the ASIC did not answer (all-ones via cs8210-pcie-errors), as on
  2026-11-10. Supporting: the CPU path (DMA rings) was already dead for 5 min; the ipd softirq storm 2 min before;
  the root port 0001:00:00.0 read UESta CmpltTO+ UnxCmplt+ (First Error Pointer 0x0e) at 16:19 on this boot.
  Not dated: the next boot (16:24, a U-Boot chainload) read UESta 0, so the bits do not survive every reboot path,
  but nobody read them on this boot before 16:00.

## 3. Hypotheses
(b) the known learn-thread wedge, unrelated to AVS: HIGH (root cause of the OOM). The 32 GiB size, the memset in
    im_malloc and overcommit = 1 explain every observation; the 2026-11-10 wedges (3 in ~10 h of vendor-stack
    runtime, no host activity near any of them, the first one 44 min after its start; this one 42 min after syncd's)
    show the trigger recurs on its own.
    What made the ASIC stop answering at 16:00:55 stays open, as on 2026-11-10.
(a) PMBus traffic on 0x62 glitched VDD core: LOW. The last PMBus transaction was at ~15:57:39, 3 min 16 s before
    the CPU path died, and nothing touched the box from 15:58:58 to 16:01:06. The rail read nominal during the
    failure (16:05:15: READ_VOUT 0x0334 = 800.8 mV, READ_IOUT 147.5 A, STATUS_VOUT 0x00, STATUS_IOUT 0x00,
    STATUS_WORD 0x1003 as at 15:57) and after; the ASIC answered BAR reads at 16:07:57 without a power cycle.
    Caveat: VOUT_UV_FAULT_LIMIT is 0, so a short dip would not have latched a UV fault. The latched STATUS_CML 0x21
    is a communication fault (PEC/memory), not a rail event.
(c) the resource0 mmap attempt or the root-port config reads: VERY LOW. The mmap failed with EINVAL before any
    access; root-port config space is on the SoC; both ended >= 117 s before the failure.

## 4. Hardening (nepeat/nix nixos/module/cs8210/sonic, deployed by the parent)
- sonic-syncd: MemoryMax = hardware.cs8210.sonic.syncdMemoryMaxMiB (default 2048; normal RSS ~330 MiB),
  OOMPolicy = stop. The memset now hits the unit's own limit within ~1 s: cgroup OOM kill of syncd only, then
  Restart=always and the recovery chain that worked at 16:05-16:06; fand and the rest keep their memory.
- sonic-cs8210-ifcs-watchdog rewritten (ifcs-watchdog.py, 48 unit checks at build; was a journal grep only). Every
  15 s: syncd VmSize >= 16 GiB (the mapping), VmRSS >= 3/4 of MemoryMax, the ifcs-learn thread >= 80 % of a core
  for two polls (the overcommit-0 spin), the old kernel line (every 60 s), and tx-stall: every oper-up port whose
  COUNTERS_DB OUT packets were rising has sent nothing for 180 s (port counter polling on, syncd up >= 300 s). On
  2026-11-16 tx-stall would have restarted syncd at ~16:04-16:05, before the bad read. One restart per 15 min;
  each trigger and each syncd restart logs the root port's DevSta/UESta/CESta (dates the next completion timeout).
- Not changed (owner/parent decisions): vm.overcommit_memory (services.redis.vmOverCommit = false would bring back
  the spin instead of the memset; MemoryMax + watchdog cover both).
- Follow-up (learn-wedge.md): the all-ones check is in our loader since (sai-teralynx learn-ring guard); the vendor
  stack's cs8210-switch got MemoryMax + OOMPolicy=stop; what died first was the CPU TX ring (full at 16:03:45), and
  the ASIC link ran with ASPM L0s and replay errors every second (cs8210-asic-aspm).
- AVS: not implicated; no change to the tool (it already sends only whitelisted commands). avs.md gets the rule
  that ad-hoc PMBus surveys of 0x62 are off-limits.
