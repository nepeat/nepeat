insmod, probe, open, DHCP, ~20 s of traffic). Box not touched for this.

Method
  nix/packages/al-eth/trace/parse.py <recording> -o hw.txt --datapath dp.txt
  difftest --hw --board hw.txt   (nix/packages/al-eth/difftest/difftest.rs)
  The control path (process context) becomes one replay scenario: the Rust
  HAL runs the same calls, its register reads are answered with the values
  the board returned (they must come in the same order at the same offsets),
  and every write, PCI config access and delay must be identical. Inputs
  taken from the recording: the 10 Toeplitz key words (get_random_bytes) and
  the descriptor ring bus addresses (dma_alloc_coherent). Rx-mode calls run in
  softirq context (netif_addr_lock_bh); their arguments are recovered from the
  MAC table entries they wrote.

Result: 0 differences.

Harness differences found while doing it (not driver differences):
  - ring bus addresses: the replay first used its synthetic addresses
    (queue DRBP/CRBP writes differed); now taken from the recording.
  - Rx buffer refill: the replay first injected the simulated scenarios'
    allocation failures (every 61st), so it posted 60 instead of 1023
    buffers per queue (doorbell 0x3c vs 0x3ff); --board turns injection off.
  - parse.py: al_eth_up_complete's own change_mtu mark is part of open; Rx
    mode marks/EC writes in softirq context are calls, not datapath.

The three C findings from code reading:
  1. hdr_split_len_sel uninitialised in al_eth_config_rx_fwd: the C wrote
     rfw.ctrl_table_def (EC +0x7ac) = 0x0000131c on this boot, bits 18:15 = 0:
     the stack garbage happened to be 0, so C == Rust here. The bug is real
     (uninitialised read) but latent in this build; not confirmed as harmful.
  2. al_eth_mac_table_unicast_add ignores its address: not observable here
     (no secondary unicast address was ever set: entries 1..3 untouched).
     Stands from code reading only.
  3. no dma_rmb on Rx completion: not visible in an MMIO recording (it is
     about memory loads); n/a.

PCI revision 0x02: confirmed by the recording too (probe ran as rev 2; the
UDMA programming id register +0x1e084 reads 0x1c360002 = rev 2).

New scenario from the recording: dmc12_board (difftest/scenarios.c): the
first value of each of the 40 non-zero registers read at probe (UDMA
revision, queue cfg/pointer reset values, M2S/S2M config defaults, EC/MAC
defaults, board params, MAC address). It drives al_udma_set_defaults' rev >= 2
branch (M2S data FIFO depth), which the zero-bank scenarios did not.
