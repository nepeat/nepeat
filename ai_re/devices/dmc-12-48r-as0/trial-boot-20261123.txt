Findings
1. CPLD watchdog (measured live): writing 0x29 while the count runs only sets the load value; writing 0x2a = 0 reloads
   the count (the kick); 0x28 0->1 starts from the load value. cpld.md's "write = load" holds, but a kick is 0x2a.
   Board hooks fixed (kick = 0x29 <- t, 0x2a <- 0). Side effect: the kick clears 0x2a b1 (fans-full after a WDT reset).
2. dmc12_cpld_reset (C, and the Rust twin: same sequence) assumes 0x28 = 0: with the watchdog already running its
   0x29<-1, 0x28<-1 does nothing and the kernel falls back to the sp805 after 2 s ("CPLD did not reset the board,
   falling back", trial ii). Harmless here (SoC reset, U-Boot's script disarms the CPLD watchdog on the default path);
   a robust sequence would write 0x28<-0 first (or kick 0x2a<-0 after 0x29<-1).
3. The verifier must run with an explicit PATH (systemd units have none): caught by the NixOS VM test, not on the box.

Tests before hardware: trial-boot-qemu-test (real alpine-v2 U-Boot + this boot.scr, 7 scenarios) and trial-boot-linux
(NixOS VM: setup/stage/cancel/status/promote refusals, verifier pass and fail->reboot), both PASS.
