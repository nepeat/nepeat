# hal: al_eth hardware logic in safe Rust

What the al_eth driver does to the hardware on our boards (DMC-12: RGMII 1G
fixed link; CS8210: SGMII, 10G serial), ported from the vendor HAL
(`../../src/al_hal_*.c`) and from the hardware-facing part of the Linux glue
(`../../src/al_eth_main.c`). `core` only, `#![forbid(unsafe_code)]`, no
panics on values read from the hardware. It reaches the device only through
the traits of `io.rs`; the kernel side (`../knet`, the driver) implements
them and does the kernel calls (net_device, NAPI, skb, DMA mapping, IRQs).

Proof of equivalence: `../../difftest` (built by `../../rust.nix`) runs the
unmodified vendor HAL C over a recording register bank, and the Rust replays
the same inputs: every register read and write (offset, value, order), PCI
config access, delay, doorbell barrier, descriptor ring entry and driver
decision must be identical. 2026-11-23: 27 scenarios, 13,198 calls,
1,936,443 lines, 0 differences; 8 of 9 hand-made mutants of the Rust are
caught (the 9th is an equivalent mutant). For the hardware: `../../trace`
records the C driver's accesses on the board; `difftest --hw --board`
replays a recorded control path (probe/open/close/stats/Rx mode) against the
Rust with the hardware's read values. DMC-12, 2026-11-23: probe, open, 8 Rx
mode changes, 3 stats reads, 46,045 lines, 0 differences
(devices/dmc-12-48r-as0/al-eth-hw-trace-diff.txt). The board's reset register
values are the `dmc12_board` scenario.

Not ported (unreached on both boards): link management, KR training,
SerDes, SFP/I2C, retimers, LEDs, SR-IOV/NIC mode (tgtid), Rx header split,
PFC, 25/40/50G and 2.5G modes, revision 1/3 paths (`Port::probe` refuses
`rev != 2`; the CS8210's rev 4 is run as 2 by the caller, as the C does).
Ported but not yet exercised by any driver: MDIO (`mac::mdio_config` only;
the C22 read/write for the CS8210's PHY needs 16-bit accesses: an
extension of `RegIo`).

## differences from the C (each on purpose)

1. **dma_rmb on Rx completion** (`CDescMem::dma_rmb`): the C reads the
   completion descriptors' other words after seeing a fresh ring id with no
   barrier (al_udma_cdesc_packet_get / al_eth_pkt_rx). Counted, not traced.
2. **Secondary unicast addresses**: al_eth_mac_table_unicast_add ignores its
   address and programs the port's own MAC into every secondary entry; the
   Rust programs the addresses. The difftest passes the own MAC as each
   address, so the register writes are compared byte for byte.
3. **Default control table entry**: al_eth_config_rx_fwd passes a stack
   struct whose `hdr_split_len_sel` is uninitialised into
   rfw.ctrl_table_def (bits 18:15 of the value are whatever was on the
   stack); the Rust writes 0 (and the C harness, which zeroes the struct).
   On the DMC-12 (2026-11-23 build) the C wrote 0x0000131c: the garbage
   happened to be 0, so the write is the same; the C bug stays latent.
4. **Errors instead of BUG/garbage**: al_assert()s and impossible hardware
   values return `Error` (no writes after the failed check), a full Tx
   slot gives the buffer back instead of overwriting it, a reserved UDMA
   state is `Error::Hardware`; when function_reset finds no board
   parameters it fails before the FLR (the C would FLR and write stack
   garbage).
5. **Not reproduced**: al_eth_free_tx_bufs' UDMA register dump when skbs are
   still pending at close (debug output); al_eth_remove's extra hw_stop
   before unregister_netdev (the Rust remove is close + nothing).
6. **Kept although odd** (so the hardware sees the same descriptors): the
   per-slot carry-over of l3/l4 protocol index and VLAN count into Tx
   packets without offload (`ring::TxSticky`); word 1 of Rx and non-first
   Tx data descriptors left as they were; u32 wrap of rx_length_errors and
   of the 10G octet corrections; u8 truncation of moderation intervals.
7. **Additions outside the C's sequences** (not in the difftest; host
   unit tests): `mac::MacTotals` (64-bit totals of the MAC's 32-bit
   counters: the C reports them raw, so rx_bytes falls at every 4 GiB
   wrap), `Port::apply_coalesce` (ethtool -C to every queue, range checked
   before any write) and `RxQueue::set_moderation` (a fixed RX interval
   with adaptive-rx off, rewritten at the next completion if an adaptive
   step raced with the switch). With adaptive moderation on (the C's mode,
   the default) the register writes are the C's.
8. **Deliberately not ported: al_eth_select_queue** (TX queue = the
   sending CPU's): it moves a flow to another TX queue whenever the sender
   migrates, which reorders it (2026-11-23 on the DMC-12: 685-989 TCP
   retransmits per 20 s of box_tx with it, 0 with the core's hash/XPS pick).

## what the kernel side must provide

- `RegIo` over the three BARs (0 UDMA, 4 EC, 2 MAC): writel/readl semantics.
- `DescMem`/`CDescMem` over zeroed coherent memory (1024 x 16 bytes),
  `publish()` = `dma_wmb()`, `dma_rmb()` = `dma_rmb()`.
- Rx buffers (`DmaBuf`) of `port::rx_buf_size(mtu)` bytes, mapped
  DMA_FROM_DEVICE; for `RxEvent::Small` sync for CPU, copy, sync for device;
  for `RxEvent::Frags` unmap and attach.
- Tx: `TxQueue::offload` before mapping, `xmit` after; free buffers given
  back by `clean`/`down`; stop the netdev queue on `XmitResult::stop`,
  wake it when `TxClean::available > TX_STOP_THRESH`.
- NAPI: `poll` then, if `complete`, `napi_complete_done` and
  `RxQueue::complete`; Tx: `clean`, `napi_complete`, `unmask`.
- `MAX_SKB_FRAGS` = 17 (CONFIG_MAX_SKB_FRAGS default): assert it.
