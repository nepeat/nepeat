## Findings

1. **must-fix (narrow) - settle + resume_account resumes the SAME account.** campaign_state.py:1148 (resume_account) uses `_OPEN_RESERVATIONS`, so once a row is settled the "unreconciled request remains globally stopped" guard no longer fires. For any account stopped with exactly `'interrupted attempt'` (the BaseException path in capture.py:434-438, e.g. a transport/observe failure that is not in the caught tuple), `settle_unobserved` then `resume_account` succeeds with no verified result (probe: stopped=None, spent_requests=1 kept). The resume_account docstring still says "after verified result reconciliation". The c4 timeout stop (`response/transport failure`) is not resumable, so c4 is unaffected, but the contract (settlement only lifts the global block) is violated for the other reason. Fix: resume_account must refuse an account that has an unobserved-settlement row (or require a reconcile_result event), and add a test.
2. **should-fix - settle cannot tell "timed out before headers" from "headers seen but observe() persistence failed".** campaign_state.py:1121-1125 only checks state=uncertain, status NULL, account stopped. A StateError inside `observe` (capture.py:~365) leaves status NULL, reason `interrupted attempt`, and a possibly unrecorded 402/403/429. Contract line ~118 says such a failure must stay fail-closed. Settling it lifts exactly that block. Fix: require the published capture_result receipt (via `_verify_receipt`, as reconcile_result does) to show a transport-class outcome (`timeout`/`unavailable`, no `status`), or restrict to stopped=='response/transport failure'. settle also skips attempt-receipt verification.
3. **should-fix - repeat call is not idempotent after any later account change.** The idempotent early return (1126) sits after the `account.stopped` check (1123). After resume_account/cancel-overwrite the repeat raises `StateError` (probe). Move the existing-event check before the stopped check.
4. **should-fix - per-account gate left on the old predicate.** resume_throttle (campaign_state.py:1048) still blocks on any non-complete reservation for the account, so a settled+resumed account can never resume a throttle. Fail-closed, so safe, but inconsistent with the new global rule; decide and document (suggest leaving it, add a comment).
5. **note - atomicity/fence/uniqueness OK.** Event insert and fence bump are one `BEGIN IMMEDIATE` txn (db(True)); a crash before commit leaves neither. Fence logic is identical to reconcile_result (keys from the original row, leases row deleted, generation+1, `legacy_recovered=1`), under `locks.held(keys)`, so the timed-out owner is fenced out. Event uniqueness is by lock+txn+pre-check only (no UNIQUE index); acceptable. Provenance string cannot be forged through record_restriction (kind limited to deny/throttle).
6. **note - cannot refund, invent a result, or unblock other states.** `_eligible`, `account()` and resume_throttle count all reservations regardless of state, so quota is never refunded (test asserts spent_requests unchanged). The row stays `uncertain` with result_id NULL. Settle refuses any row with state != uncertain or a status (test 2), and reconcile_result still refuses status-less rows. Residual dead end: a process killed in `dispatch_admitted` (no uncertain() call) is neither settleable nor reconcilable and blocks all admissions forever; needs a separate recovery path (out of scope here, worth a PROGRESS note).
7. **note - other gates.** relocate (509), `_eligible(new=True)` (816, so activate() and reserve() too) and resume_account use the new predicate; require_production_ready, synchronize_archive, upgrade/migrate, campaign.py and coverage.py do not query reservations. No test settles then relocates; add one line.
8. **note - honesty of the timeout record.** Reservation is committed (charged) and the attempt receipt published before dispatch; the result receipt records outcome `timeout`, error `TimeoutError`, `actual_bytes=0`. The server may still have processed the CSV POST (or issued a 429/403 we never saw); the design records "charged, uncertain, account stopped", which is honest. `actual_bytes=0` could be misread as "nothing happened"; the decision text should say the request may have reached the server. A distinct follow-up attempt re-sends the same POST under a new cycle: that is the intended "distinct bounded attempt", but there is no cross-account request cap or pacing, so the coordinator must allocate it deliberately.
9. **note - Location redaction.** `location` in `_SENSITIVE` drops any dict key named location (case-insensitive) at any depth in receipts and adds the header value to the diagnostic redaction list. Checked data/archive/receipts: no existing key named `location` (only `original_location`, `xml-locations`), so no existing receipt ID or legacy provenance hash changes. Residual risk: a future saved-failure row with a `Location` header gets a different legacy provenance hash than before. tests/test_capture.py redirect test passes.
10. **should-fix (driver) - cost report is lost on failure and counts worst-case bytes.** live_rra.py: the JSON report is written only after the whole phase returns (line ~131) with `open('x')`; an unexpected exception, or an existing report name, after live requests were charged leaves no cost record. Wrap capture in try/finally and write a partial report. `account_state.spent_bytes` is the worst-case charge (2,000,002 for 2 requests), not measured bytes; also record per-step actual_bytes from receipts.
11. **note (driver) - caps/windows OK.** requests=4+n (one spare over the 3+n plan), byte_limit and host limit = requests*(MAX_BYTES+1) match `reserve()` (max_bytes+1); window=1800 elapsed seconds is enforced by `_eligible`; runner returns on first non-success (no retries); bundle target dir created with exist_ok=False under data/raw/*-live-<cycle>; precondition 3 (explicit 3+n pre-check) is replaced by the durable cap, acceptable. A reused cycle id re-opens the same account (allocate is idempotent) and yields `new_observations=0`; the driver still goes on to bundle, so check that field before treating it as a refresh.
