## readiness and gaps, grounded in code

**what genuinely exists.** immutable objects and receipts with hard-link publication and conflict detection (`devicehunt/artifacts.py:68`), a reconstructible index, a bounded collector with per-request and per-host leases, saved-failure ingestion, conditional 304 reuse and distinct unavailable/empty/invalid/timeout/throttled outcomes (`devicehunt/capture.py:137`), two local recipes, a frozen release validator that checks selector excerpts against saved bytes (`devicehunt/lineage.py:68`), and importers that validate every sibling dependency before a transactional source replacement. the rra collector already pins a query by manufacturer plus `fromdate`/`todate` and proves stability with byte-identical before/after csv exports (`research/capture_rra_query.py:44`, `:84`). that is the closest thing in the repo to an incremental regulator unit.

**gaps that block an ongoing campaign.**

- **receipt scans are linear and repeated.** `Archive.receipts()` globs and parses every json in a flat `receipts/` directory (`artifacts.py:166`). `Collector._rows` calls it, and one `capture()` calls `_rows('capture_result')` up to six times (`capture.py:143-193`). fine at 374 receipts, quadratic across a campaign. the sqlite index already holds the receipts table but is never read for this.
- **every writable open reindexes the whole archive** under `BEGIN IMMEDIATE` (`artifacts.py:114`, `:247`). two collectors opening the same archive serialize on a full rescan each.
- **throttle is permanent.** any `capture_result` with outcome throttled for a host raises `StopCollection` forever (`capture.py:143`), with no reviewed resume path. one 429 kills a regulator for the rest of the project.
- **budget is instance memory only** (`self.remaining`, `capture.py:85`). a crash loses nothing but also persists nothing; two concurrent collectors each get a full budget.
- **crash signature exists but nothing reads it.** an interrupted request leaves a `capture_attempt` with no `capture_result` (proven in `tests/test_capture.py:83-87`). no report lists those.
- **freeze is all-or-nothing.** `archive.freeze` snapshots every artifact and every receipt in the archive (`archive.py:119-132`). a second release would embed the whole first one.
- **lineage follows import, not the reverse.** `prepare()` requires the projected fact to already exist in the catalog (`lineage.py:118`), so statements can only be reviewed after a candidate import. the campaign order must respect that.
- **only the sitemap adapter uses the shared collector.** the rra and ised scripts shell out to curl or keep an in-memory cookie jar and write their own progress files. ised's post/refresh/cookie flow does not fit `fingerprint()` because every header is identity (`capture.py:15`).
- **no shipment/customs adapter or qualifying source.** the only trade evidence is secondary previews and a saved eximpedia 402 (`research/bytedance-inspur-2026-10-04.md:52-59`).

## smallest architecture, then phases

**campaign state is a pinned manifest plus the receipt ledger, not a new database.** one json per regulator under `research/campaigns/<regulator>.json` declares finite units: for rra, (manufacturer spelling, fromdate, todate) windows; for ised, company query strings; for each unit, the saved bundle path and hash if already captured, known failures, a per-batch request ceiling, and a stop rule. the archive receipts remain the only mutable ledger, append-only. a read-only `status` command derives per-unit state from receipts: saved, success, not_modified, unavailable, blocked, throttled, interrupted (attempt without result), not_attempted. coverage is the fraction of declared units in a terminal state. freshness is the newest result timestamp per unit against the manifest's declared window end, never an automatic refresh.

**incremental adapter contract.** an adapter is a module exposing `units(manifest)` returning finite url sets with validators, `register_saved(collector, unit)` for existing captures, and `bundle(unit, receipts)` producing the existing importer's input so `rra.validate` and friends stay the gate. rra windows must be contiguous and non-overlapping per spelling because the importer derives a new source id from the query digest (`devicehunt/rra.py:173`); overlapping windows would duplicate certificates across sources. `Policy.allowed_urls` stays an exact frozenset, which is the pinning mechanism.

**persistent budget, leases, crash semantics.** add a `campaign` tag to `Policy` carried into `capture_attempt` payloads; the collector computes remaining as ceiling minus tagged attempts already in the ledger, re-read after lease acquisition. attempts count even when interrupted, so crashes are conservative. leases already recover by expiry. throttle gets an explicit `capture_policy` receipt of kind `throttle_release` naming host, reviewer and a timestamp; `capture()` ignores throttled results older than it.

**archive index consistency.** `_rows` reads the sqlite index, guarded by a cheap staleness check (receipt file count versus indexed rows) that falls back to reindex on mismatch. writable open stops reindexing unconditionally. shard new receipts into `receipts/<first two of id>/` with `rglob`, keeping flat legacy files readable. receipts stay authority, the index stays disposable.

**review and release selection.** adapters never write statements. a researcher writes candidate statements as json in their batch directory with `lineage.identity` ids; a different reviewer writes review records. `freeze` gains a selection of statement ids and includes only their receipt closure via `receipt_references`, so each batch release is small and `archive_release_*` rows stay per batch.

**phases, with owners and gates.**

1. **manifest and docs, no code.** owner: documentation editor. write `docs/campaign-plan.md` and the two pilot manifests. pin rra: existing eight spellings at `19900101`–`20260926` as saved units, one new window per spelling from `20260927` to a user-chosen end date. pin ised: the five existing queries as saved units. gate: manifests list every saved bundle hash and every known failure. stop: no new captures.
2. **engine hardening.** owner: engineer A, paths `devicehunt/capture.py`, `devicehunt/artifacts.py`, their tests. deliver campaign tag, ledger budget, throttle release, indexed `_rows`, conditional reindex, sharded receipts. gate: existing suite passes; new tests cover two collectors sharing one ceiling, release honored only after its timestamp, interrupted attempt visible, flat and sharded receipts both load; a synthetic archive with a declared receipt count opens without rescan. report measured timings, promise nothing.
3. **campaign module and offline registration.** owner: engineer B, paths `devicehunt/campaign.py`, `research/campaign_rra.py`, `research/campaign_ised.py`, `tests/test_campaign.py`. register the nine rra bundles and ten ised captures through `register_saved` the way `research/fetch_fcc_sitemaps.py:65-70` does. gate: offline run asserts zero transport calls; status accounts for every declared unit; overlapping rra windows rejected. depends on 2.
4. **selective freeze.** owner: engineer A, `devicehunt/archive.py`, `tests/test_archive_release.py`. gate: a selection's closure validates with `lineage.prepare`; a link outside the closure fails. independent of 3.
5. **first live rra window.** owner: researcher, new `data/raw/rra-<spelling>-<window>/`; integrator promotes. budget per spelling is finite from the csv: three requests plus one per certificate. gate: before/after csv equal, every detail page validated by `rra.validate`, candidate rebuild equal to clean rebuild via `scripts/compare_rebuild.py`, statements reviewed by someone other than the author. stop: throttle, 402/403, or budget. depends on 2, 3, 4.
6. **ised live, conditional.** needs a contract extension for session headers excluded from identity and adapter-level polling where each refresh is a budgeted request. do not start until 5 is accepted.

## pilot choice, trade stage, limits, risks

**two-regulator pilot: korea rra and canada ised.** rra is the strongest fit in the repo: an official regulator, date-bounded queries, a documented detail url pattern, nine saved bundles already in `data/import-manifest.json`, and a stability check that doubles as a freshness primitive. ised is the second format: html plus csv under a session, five validated captures with documented discrepancies, and an importer that already checks contiguous pages and stable totals (`research/ised-radio-equipment.md:52-58`). it stresses the adapter contract in exactly the way rra does not, which is why it goes offline-first and live-last. the fccid.co sitemaps are a mirror with known omissions and ten 400s, not a regulator, and remain the existing demo rather than a pilot member. no live capture is needed for phases 1 through 4.

**trade feasibility stage.** owner: one researcher, output a source qualification record, no adapter. two classes kept apart: aggregate statistics, which can at most become context facts and can never name a model, party or shipment; and shipment-level records with party and product fields, which require a free primary publisher, stable record keys, snapshot dates and local-retention terms before any raw table is designed. feasibility is unknown and not researched this pass. the record must allow the outcome no qualifying source, which closes the stage with a note and leaves the volza/eximpedia leads as leads. the saved eximpedia 402 stays blocked.

**storage and release limits.** each batch declares a maximum of new object bytes and new receipts in its manifest; status reports actuals and the integrator refuses promotion past the ceiling without a user decision. one candidate database per batch, archived through the storage tool after promotion per `docs/archive-storage.md`, no new loose sqlite files. one release json per batch with selective closure. operational checks before promotion: `archive audit` clean, no staging files, no interrupted attempts unexplained, lease table empty.

**risks and expected disagreements.** a campaign-runner-first approach will be proposed. i disagree with building it before phases 2 and 4: the bottleneck here is review and exclusive integration, not fetching, and a runner would pile unreviewed receipts into a flat directory that scans linearly, with pressure to auto-promote. a second disagreement: migrating all 45,017 historical facts to reviewed lineage. do not; attach lineage only to facts a campaign batch touches. a third: treating rra's byte-identical csv as proof of regulator completeness. it proves query stability only.

**what not to build yet.** a scheduler or daemon, a generic crawler of the 190,198 sitemap detail urls, ocr, automatic entity or alias matching, a trade adapter, a web ui, ised live support before the header contract exists, and any new catalog schema beyond the release tables already present.

this is planning only. nothing was written, run or fetched.
